# AI 一线节点协同终端：96 小时功能排期表

## 1. Strategy Context

### 1.1 目标

在 96 小时内交付一个可重复演示的“纸张＋实体终端＋分层权限工作流”闭环：

> 纸质图纸/工单绑定 → 师傅在实体终端确认 → 师傅语音上报异常 → 小组长审核 → 小组长升级厂长 → 厂长人工指派专业资源 → 资源提交处理结果 → 小组长确认并通知师傅 → 师傅确认、工单恢复 → 完整数字脚印和事件时间线。

### 1.2 本期唯一产品结果

评委能够确认：这不是一块“小屏幕通知器”，而是一套 **由同一任务、权限和状态引擎驱动的轻量级执行与追溯系统**。师傅端做极简高频动作，小组长/厂长/专业资源使用网页或手机端处理同一任务流，老板看同一事件源生成的关键指标。

演示价值表述统一为：

- 让问题更早暴露并进入正确责任链。
- 让每个工序留下可还原的数字脚印。
- 让过程透明、便于提前纠偏，而不是事后追责。

### 1.3 团队与约束

三名成员按整合责任域协作，不设置四个互相独立的岗位：

- **成员 A：产品 / 前端 / 演示**
- **成员 B：后端 / AI / 工作流**
- **成员 C：硬件 / 通信 / 集成**

共同约束：

- 96 小时包括范围冻结、实现、联调、测试、路演物料和缓冲。
- 至少一台实体终端必须触发真实后端状态变化。
- 先用固定数据与手工表单跑通权限链，再接语音和 AI；AI 不能阻塞主路径。
- H72 后原则上禁止新增功能。
- 本期不证明真实工厂 ROI，也不宣称工业级量产或跨厂产品化已经完成。

## 2. Definition of Done

只有同时满足以下条件才算完成：

- [ ] 一张演示纸图/工单拥有唯一 Work Order ID、Drawing Revision ID 和二维码/NFC 绑定。
- [ ] 真实终端能显示项目/部件摘要、版本有效状态，并完成师傅确认。
- [ ] 真实终端能触发异常语音/文本上报，系统自动关联项目、部件、版本、工单、节点、人员和时间。
- [ ] AI 能生成可编辑异常摘要；AI 失败时手工流程仍可完成。
- [ ] 异常先进入小组长队列，由小组长人工升级厂长。
- [ ] 厂长人工选择并指派一种专业资源，AI 不自动派工。
- [ ] 专业资源提交结果后，小组长确认并通知师傅。
- [ ] 师傅在真实终端收到强反馈并确认，工单从阻塞恢复到执行中。
- [ ] 时间线完整记录绑定、确认、上报、审核、升级、派工、处理、结果确认、师傅确认和恢复。
- [ ] 看板能显示当前责任节点、上下文完整状态和本次异常总阻塞时长。
- [ ] 权限测试证明师傅不能直接联系/指派设计师，专业资源不能直接改变师傅工单状态。
- [ ] 连续 10 次端到端演示无阻断、无重复事件、无越权流转。
- [ ] 有可重置演示数据、软件模拟终端和 90 秒离线录屏；现场仍至少展示一次真实硬件状态变化。

## 3. 功能优先级

### 3.1 P0：必须完成

| ID | Initiative | Outcome | Acceptance signal |
|---|---|---|---|
| P0-01 | 演示对象与纸张绑定 | 纸图拥有可计算身份和版本状态 | QR/NFC 可解析 Work Order 与 Drawing Revision |
| P0-02 | 四角色权限与双状态机 | 全端共享同一业务事实且不越权 | Work Order / Exception 状态、角色权限和事件唯一 |
| P0-03 | 师傅实体终端 | 一线不用手机完成确认、异常和恢复确认 | 至少一个硬件动作改变真实后端状态 |
| P0-04 | 语音异常结构化 | 异常自动携带现场上下文 | 原文保留、字段可改、失败可手工降级 |
| P0-05 | 小组长审核与升级 | 异常遵循第一责任接口 | 小组长实际完成一次审核和升级 |
| P0-06 | 厂长资源调度 | 厂长保留跨部门派工权 | 人工创建 Resource Assignment，可撤回/重派 |
| P0-07 | 资源处理与结果返回 | 处理结果沿原责任链返回现场 | 资源提交→组长确认→师傅确认→工单恢复 |
| P0-08 | 数字脚印与老板看板 | 过程可还原、阻塞可定位 | 完整时间线＋当前节点＋总阻塞时长 |
| P0-09 | 演示重置与稳定性 | 现场不依赖临时修复 | 10 次连续成功＋模拟端＋离线录屏 |

### 3.2 P1：P0 稳定后再做

| ID | Feature | Entry condition | Cut rule |
|---|---|---|---|
| P1-01 | 图纸版本变更广播/旧版召回 | H60 前 P0 全链路稳定 | H72 前不稳定即隐藏 |
| P1-02 | 图片证据上传 | 语音和返回链已稳定 | 不改硬件即可完成，否则砍掉 |
| P1-03 | 超时提醒和队列优先级建议 | 事件时间与状态可靠 | 只提示，不自动升级或派工 |
| P1-04 | 第二套节点/异常配置 | 首个场景数据不再改 Schema | 仅展示配置替换，不做控制台 |
| P1-05 | Excel 导入导出/模拟回写 | 核心事件存储稳定 | 无真实系统时只显示日志 |

### 3.3 P2：赛后探索

- 完整 CAD 解析、尺寸识别和小屏看图。
- 生产级硬件、工业认证、量产外壳和设备批量运维。
- 真实 ERP/MES/PLM/CAD 图纸台账集成。
- AI 自动派工、自动越级、自动质量归因和处罚。
- 完整多工厂配置控制台与模板市场。
- 摄像头视觉质检、数字孪生和复杂排产。
- 同时适配多个行业或证明真实工厂 ROI。

```mermaid
flowchart LR
    A["冻结真实场景与三分钟故事"] --> B["冻结对象、权限和双状态机"]
    B --> C["固定数据跑通手工全链路"]
    C --> D["真实终端完成绑定与状态触发"]
    D --> E["语音异常接入"]
    E --> F["AI 结构化＋人工确认"]
    F --> G["时间线与关键指标"]
    G --> H["连续演练与减法"]
    H --> I["功能、数据和路演冻结"]
```

> 最关键的竖切不是先做 AI，而是“真实硬件确认 → 组长看到 → 厂长派工 → 资源处理 → 结果返回硬件”。任何智能能力都必须挂在这条确定性链路上。

## 7. Scope-cut Gates

### H12 Gate

- 若软件模拟端尚未跑通完整权限链：停止视觉精修、AI 和全部 P1，只修对象、状态、权限和 API。
- 若硬件方案仍不确定：锁定一种绑定方式、一种输入和一种反馈，不再扩充传感器。
- 若真实案例字段不完整：使用明确标注的脱敏演示数据，不临时扩展领域模型。

### H24 Gate

- 若真实终端不能接收对象并触发状态：减少到“版本显示＋确认/异常二选一”最小硬件动作，其余先用模拟端。
- 若实时通信不稳定：使用短轮询或显式刷新；不在黑客松内重构通信架构。
- 若角色页面过多：合并为一个带角色切换的 Web 控制台，但后台权限校验不能删除。

### H48 Gate

- 若语音识别不稳定：保留语音入口和原音，使用可编辑转写或文本降级。
- 若 AI 结构化不稳定：限制预设异常类型；保留“AI 建议＋人工确认”，不得让 AI 成为单点故障。
- 立即取消摄像头、视觉识别、CAD 解析、自动归因和自动派工。
- 不允许为了保留 AI 而删除“小组长审核—厂长派工—结果返回”权限链。

### H60 Gate

- P0 未全链路跑通：所有 P1 清零，老板看板只保留当前节点和总阻塞时长。
- P0 已跑通但不稳定：只修阻断、重复事件、权限、错误恢复和设备连接。
- 若一台以上硬件增加风险：只保留一台真实终端，其余角色全部 Web 化。

### H72 Gate

- 功能冻结，禁止新增需求、模型字段和硬件能力。
- 任何不能稳定解释或没有参与主演示闭环的功能从入口隐藏。
- 只允许阻断级修复、演示数据重置、录屏和讲稿减法。

## 8. Test Plan

### 8.1 Functional and Permission Cases

| Case | Expected result |
|---|---|
| 扫描/碰触有效纸图 | 显示正确项目、部件、版本和工单；确认事件唯一 |
| 使用失效图纸版本 | 终端明确警示；不能静默确认为有效 |
| 师傅重复确认/重复上报 | 每个业务动作只生成一个有效事件 |
| 师傅上报异常 | 工单进入阻塞；只进入所属小组长队列 |
| 师傅尝试直接指派设计师 | 权限拒绝并记录，不创建 Resource Assignment |
| 小组长审核并升级 | 记录 Escalation 原因、人员、时间和完整上下文 |
| 小组长尝试跨部门指派 | 权限拒绝；只有厂长可派专业资源 |
| 厂长指派/重派 | 生成 Assignment 与 Decision；历史保留 |
| 专业资源提交结果 | 回到原责任链；不能直接恢复师傅工单 |
| 小组长确认、师傅确认 | 终端收到强反馈；师傅确认后工单恢复执行 |
| AI 转写/结构化失败 | 原始输入保留，手工编辑后仍能完成闭环 |
| 结果被退回 | 异常保持处理中或待调度，工单保持阻塞 |
| 网络短暂中断 | 显示失败/待同步，不误报完成；可按降级方案继续 |
| 演示重置 | 回到同一初始对象和状态，不残留前次事件 |

### 8.2 Demo Reliability

- 连续执行主演示 10 次，记录每次耗时、故障点、恢复方式和重复/越权事件。
- 三名成员各自完整执行至少 1 次；另找一名不了解代码的人执行 3 次关键动作。
- 在现场投屏、网络、电源、噪声和麦克风条件下各演练一次。
- 准备同版本、同数据、同故事的 90 秒离线录屏，不能展示比现场更多的未交付功能。
- 设备断开后，模拟端能继续说明软件链路；但最终演示至少一次真实硬件事件。

| Member | Primary responsibility | Must deliver | Backup responsibility |
|---|---|---|---|
| A：产品 / 前端 / 演示 | 范围、真实案例、纸图样张、角色 Web 端、老板看板、验收、讲稿与物料 | 角色切换控制台、时间线/指标、3 分钟故事、可重置演示操作手册 | B 出问题时用手工表单/调试页保住故事；C 出问题时切模拟终端 |
| B：后端 / AI / 工作流 | 领域模型、状态机、权限、API、事件日志、AI 结构化、指标计算、重置 | 确定性全链路、幂等审计、人工降级、语音/文本结构化 | A 页面故障时提供调试页；C 通信故障时提供设备模拟接口 |
| C：硬件 / 通信 / 集成 | QR/NFC、屏显、输入、录音、震动/灯光、设备协议、电源和现场集成 | 一台真实终端稳定完成绑定、状态触发、异常入口和恢复反馈 | 用模拟固件/串口脚本定位；帮助 B 验证通信重试与幂等 |

### Working Rules

- 每个模块只有一个 DRI；协作不等于多人同时改同一关键路径。
- 每 6 小时进行一次 10 分钟风险同步，只讨论阻断、依赖、砍项和下一出口条件。
- 三人共享一份状态/权限表、一套演示数据和一个事件源，禁止各端自行发明状态。
- 每位成员安排正常睡眠/轮休；H72 后疲劳开发只会增加演示风险。
- H72 后任何阻断级修改必须由改动者和受影响端负责人共同验证。

## 12. Risks & Dependencies

| Risk / dependency | Why it matters | Response |
|---|---|---|
| 权限链太长，96 小时难稳定 | 任一步失败都会破坏主演示 | H36 前先完成无 AI 手工链；只用一个异常和一种资源 |
| 硬件增加吸引力但没有购买价值 | 容易被评为“硬件为了硬件” | 强调同一任务流和状态变化；赛后做替代终端对照 |
| “数字脚印”被理解为追责监控 | 影响工人采用和评委价值判断 | 统一表述为早暴露、早纠偏、过程还原；不做处罚 |
| 厂长队列可能成为新瓶颈 | 数字化可能放大而非解决等待 | 记录升级率、派工时间和当前队列；允许组长班组内解决 |
| 语音、网络、硬件是三个单点故障 | 现场环境不可控 | 原音/文本降级、短轮询/显式刷新、模拟端和录屏 |
| 三人前端工作过载 | 角色页面和物料集中在 A | 使用一个角色切换控制台和共享组件，不做四套独立 App |
| 不同工厂差异超出配置层 | 商业化滑向高实施项目制 | 第二家工厂做复用审计，不在黑客松提前宣称壁垒 |
| 缺真实基线 | 无法证明 ROI | 黑客松只证明闭环；试点前采上下文、升级、派工、阻塞和错版基线 |
