## 1. 当前版本结论

MVP v0.1 是一个**可交互、部分能力已接入真实后端的功能验证型 MVP**，不是纯静态设计稿，也不是可直接规模运营的生产产品。

本版已经能够证明以下产品逻辑：

1. 用户以可复用的“协作护照”表达此刻状态、能力证据和公开边界；
2. 用户在手机“发现”中浏览人、附近和活动名册，并自行设置硬性门槛；
3. 线上“想认识”和线下碰卡是两条独立路径，不互为前置；
4. 碰卡只建立真实相遇关系，不自动入队或替人决定项目；
5. 项目方向未确定时，必须先由人完成意图澄清并由双方确认方向；
6. Agent 只提出角色和任务建议，成员可以认领、调整、拒绝并最终确认；
7. COSPAN Space 负责把关系启动成行动，不取代飞书、GitHub、微信或完整项目管理工具。

本版仍不能证明：

- 真实活动用户会持续使用或愿意付费；
- 实体 NFC／数字工牌已经完成端到端联调；
- 公网账号、定位、消息和隐私体系已经达到生产要求；
- Agent 已经在真实团队中持续完成任务路由；
- 主办方中台、跨活动复用和长期贡献体系已经成立。

## 2. MVP 核心假设

### MVP-H01：身份复用假设

参加不同活动的用户不愿反复填写相同资料；一份由本人持续维护、按活动授权的协作护照，可以降低重复建档成本。

### MVP-H02：解释式发现假设

在黑客松语境中，用户更需要“为什么值得聊、有什么证据、还要确认什么”，而不是一个无法标准化的匹配百分比。

### MVP-H03：真实行动假设

线上右滑只能表达意愿；面对面碰卡是双方已经交流后的真实行动，能够承担相互介绍和直接建联，但不代表自动组队。

### MVP-H04：从关系到行动假设

建联后立即进入方向确认、入队和首次分工，比只交换联系方式更能产生有效协作结果。

### MVP-H05：人类主权假设

Agent 的价值是整理上下文、提出候选分工和提示风险；方向、成员、负责人、重大变更和历史删除的最终决定权必须留给人。

## 3. 已冻结产品原则

### MVP-P01：手机是主交互终端

- 手机承接发现、附近、名册、连接、协作确认、SOS 和个人资料；
- 附近定位等高功耗能力只在手机前台、用户授权且页面需要时运行；
- 数字工牌不扫描附近人员，不显示雷达或完整名册。

### MVP-P02：手机端保持四个一级入口

1. **发现：** 推荐、附近、活动名册，以及后续的人／急招／SOS 内容；
2. **连接：** 待回应、已建联和相遇上下文；
3. **协作：** 项目邀请、启动进度、任务确认、关键动态和 SOS；
4. **我的：** 协作护照、公开状态、能力证据、平台链接和工牌预览。

碰卡不是第五个 Tab；协作护照也不是独立 Tab。

### MVP-P03：不公开展示综合匹配度

- 用户可以设置距离、状态、能力和证据等硬门槛；
- 系统不得静默放宽用户设置的硬门槛；
- 用户看到推荐理由、证据和待确认问题，不看到“87% 匹配”等综合评分。

### MVP-P04：意愿、建联和入队是三次不同决定

- 右滑／“想认识”只表达单方线上意愿；
- 双方主动碰卡可以直接建立 `physical_mutual` 真实相遇连接；
- 被动 NFC／QR 打开页面只允许查看授权资料和发起请求；
- 任何 Connection 都不自动产生 Project Membership；
- 被邀请者必须再次确认，才能加入项目。

### MVP-P05：方向未定时先澄清，不先建项目

双方需要明确并确认：

1. 服务谁；
2. 解决什么问题；
3. 验证什么结果。

方向草案确认前，不创建项目、不邀请入队、不生成正式任务和负责人。已有明确项目方向时，可以跳过该步骤，但入队确认仍不可跳过。

### MVP-P06：Agent 建议，人类决定

- Agent 输出的是 `Assignment Proposal`，不是正式任命；
- 成员可以因兴趣主动认领没有经验的任务；
- Leader 或成员不能让 Agent 无痕覆盖已确认计划；
- 历史存档、方向切换和大范围重排属于后续多人确认治理，不进入本版自动执行。

### MVP-P07：COSPAN Space 是启动舱，不是飞书替代品

COSPAN Space 只负责：

- 已确认方向与团队上下文；
- 首次角色和任务建议；
- 人类认领、调整和基线确认；
- 关键变更、贡献与 SOS 的必要记录；
- 向飞书、GitHub 等执行工具交接。

聊天、在线文档、代码托管和长期任务维护不在 MVP v0.1 范围。

### MVP-P08：硬件可删除

没有 NFC 或数字工牌时，二维码和普通链接仍必须能完成同一软件闭环。硬件负责降低现场摩擦，不是产品成立的前提。

## 4. 当前用户闭环

```text
加入一场活动
→ 组装并授权协作护照
→ 在发现页浏览推荐／附近／名册
→ 线上表达“想认识”，或在线下直接碰卡
→ 建立协作连接
→ 判断项目方向是否已经明确
   ├─ 否：双方完成人类意图澄清并确认方向草案
   └─ 是：继续下一步
→ 创建项目或选择已有项目
→ 发出项目邀请
→ 对方确认入队
→ Agent 提出角色覆盖、风险和首批任务建议
→ 成员认领／调整
→ 全员确认首版计划基线
→ 开始执行，必要时发布项目 SOS
```

### 4.1 线上路径

`浏览人物 → 右滑想认识／发送招呼 → 对方回应 → 建立 Connection`

### 4.2 线下路径

`双方已经交流 → 主动碰卡 → 相互介绍 → 直接建立 physical_mutual Connection`

线上意愿不是线下碰卡的前置条件。被动读取单张 NFC 卡或二维码不属于双方主动碰卡，仍要经过请求与接受。

### 4.3 建联后的项目路径

- **方向未定：** 进入意图澄清，双方确认后创建项目；
- **已有项目：** 选择已有项目并发出邀请，不重复创建同名项目；
- **任何情况：** 受邀者本人确认后才成为团队成员。

## 6. 数据与技术基线

### MVP-T01：前端

- 响应式 HTML／CSS／JavaScript 手机原型；
- 同一套界面支持手机宽度和宽屏 COSPAN Space；
- 静态模式状态保存在内存，刷新后重置；
- Live 模式已接入可见状态、平台链接和附近定位。

### MVP-T02：后端

- Node.js 内置 HTTP 服务和 HTTP／JSON API；
- 关键状态由服务端校验，不依赖前端隐藏按钮；
- Bearer 演示会话、独立设备密钥和受保护 Demo Reset；
- 确定性规则和模板 fallback 保证 AI 不可用时主链仍成立。

### MVP-T03：数据

- SQLite 单机数据库；
- 记录活动、用户、资料授权、位置心跳、卡片、请求、连接、项目、邀请、成员、任务、SOS 和 Event Log；
- 数据库文件保存在服务器持久磁盘，不随发布包覆盖；
- 公开多人运行前评估迁移 PostgreSQL／Supabase。

### MVP-T04：部署

```text
http://49.233.197.225/
├── /              → 手机 H5
├── /api/*         → Node.js API
└── /c/*           → NFC／QR 有限公开页
```

- Nginx 对外监听 80；
- Node.js 只监听 `127.0.0.1:8787`；
- systemd 负责服务常驻；
- SQLite 位于 `/var/lib/rally/demo.sqlite`；
- 线上演示身份不允许使用不安全兼容头。

### MVP-G1：阻断规模化活动

| 缺口编号 | 缺口 | 完成标准 |
|---|---|---|
| MVP-G1-01 | 多活动和活动授权 | 用户明确选择参加活动；活动之间的数据授权彼此隔离 |
| MVP-G1-02 | 实时消息和通知 | 请求、邀请、任务确认和 SOS 有可靠通知或轮询降级 |
| MVP-G1-03 | 真实匹配数据 | 排序基于已授权资料和活动需求，不依赖演示角色常量 |
| MVP-G1-04 | 真实 Agent 服务 | 结构化输出、超时、成本、审计和模板 fallback 可观测 |
| MVP-G1-05 | 内容与安全运营 | UGC 审核、举报、封禁、滥用限频和活动规则开关完整 |
| MVP-G1-06 | 埋点与漏斗 | 有效协作结果、隐私护栏和来源归因可查询 |

### MVP-G2：后续产品扩展

- 跨活动贡献证据和长期协作关系图谱；

- 悬赏支付、托管和争议处理；
- 数字工牌量产、固件升级和设备管理。

## 9. MVP 产品验证指标

### MVP-M01：北极星结果

**有效协作结果数（Effective Collaboration Outcomes）**：双方建立 Connection 或 Aid Session 后 72 小时内，至少发生一种结果：

- 接受项目邀请；
- 进入同一项目并接受至少一个共同任务；
- 支援者接受 SOS、实际开始援助，并由发布者确认达到预先声明的解决标准。

### MVP-M02：首场真实活动只采集基线

当前没有真实用户数据，不为以下指标伪造目标：

- 协作护照完成率和公开授权率；
- 推荐曝光到人物详情、请求和接受的转化；
- 建联到入队／任务认领的转化；
- 从入场到完成组队的中位时间；
- NFC、QR 和线上推荐的增量差异；
- SOS 首次有效响应时间和解决率；
- 活动后 7 日／30 日协作复用率。

首场小规模内测的任务是建立真实基线，并判断用户是否认为新增的方向确认和分工环节带来价值，而不是多此一举。

### MVP-M03：零容忍护栏

- 未授权资料曝光：0；
- 过期状态继续推荐：0；
- 拉黑后继续推荐或请求：0；
- 未确认方向即创建项目／生成任务：0；
- 未确认入队即生成 Membership：0；
- AI 生成不存在事实后直接公开：0；
- 禁止付费支援的活动仍出现有偿入口：0。

## 10. 本版明确不做

1. 不做主办方管理中台；先完成 To C 产品闭环；
2. 不做完整聊天、群聊、文档和通用项目管理；
3. 不做公开人格、能力或匹配百分比评分；
4. 不做 Agent 自动建联、自动入队、自动派活和自动覆盖计划；
5. 不做实际悬赏支付、资金托管和抽佣；
6. 不让数字工牌承担附近雷达、名册或高功耗发现；
7. 不将项目发起人永久等同于 Leader；
8. 不在未经多方确认时删除历史存档或大范围重排已确认工作；
9. 不宣称当前版本已达到生产级安全、稳定性或规模能力。

## 11. 下一版本建议

### MVP-v0.2：真实小范围内测版

优先顺序：

1. 正式域名、HTTPS 和最小账号体系；
2. 把连接、意图、邀请、Room 和 SOS 手机界面全面接入后端；
3. 完成 QR 和普通 NFC 标签的双机实测；
4. 选择一场小规模活动跑真实用户闭环；
5. 补齐事件漏斗和隐私护栏监控；
6. 根据真实摩擦决定是否继续保留意图澄清、COSPAN Space 和数字工牌。

不建议在 v0.2 前优先投入：主办方中台、完整 Leader 治理、正式支付、复杂 Agent 编排或硬件量产。
