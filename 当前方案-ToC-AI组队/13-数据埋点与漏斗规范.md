# COSPAN 数据埋点与漏斗规范

## 1. Overview

**范围：** 演示版手机端、H5/WebView 与后端的第一方行为埋点。<br>
**当前活动：** `hackathon-2026`。<br>
**当前线上地址：** `https://49.233.197.225`。<br>
**命名约定：** `snake_case`，使用“对象＋动作”，例如 `connection_requested`。<br>
**状态：** 已按本文档完成第一方埋点、受保护汇总／CSV 导出和自动化测试；待部署后进行真实手机验收。

### 1.1 Analytics Goals

埋点必须能够回答以下问题：

1. 真实用户能否完成“短信请求 → 验证成功 → 进入活动”；
2. 用户能否完成最小协作资料并明确授权公开；
3. “发现 → 详情 → 请求 → 接受”的真实转化和主要流失点在哪里；
4. 建联后是否真正发生“项目创建／邀请 → 入队 → 启动协作 → 接受任务”；
5. NFC、QR、在线推荐等来源的转化是否可区分；
6. 是否出现未授权曝光、重复建联、未确认入队等零容忍问题；
7. 演示现场是否存在短信、弱网、接口失败或事件漏报。

### 1.2 第三方平台决策

**结论：演示阶段不接入第三方埋点平台，采用第一方采集。**

| 选项 | 本阶段决策 | 原因 |
|---|---|---|
| 自建轻量采集：现有 Node.js 后端＋SQLite | 采用 | 无新增账号和外部域名；与当前部署一致；可直接验证完整漏斗和导出答辩证据 |
| PostHog / Mixpanel / Amplitude | 暂不接入 | 演示阶段收益不足以覆盖 SDK、网络、数据处理协议和隐私评估成本 |
| GA / Firebase Analytics | 暂不接入 | 当前重点是身份、建联和组队的业务漏斗，而非通用页面流量；还会增加外部依赖 |
| 自托管 PostHog | 赛后候选 | 当需要可视化漏斗、留存、路径分析或多个活动横向比较时再评估 |

第一方方案不是继续复用现有 `event_logs` 作为万能表：

- `event_logs` 继续承担业务审计、状态迁移和幂等证据；
- 新建 `analytics_events` 保存行为曝光、漏斗事件和客户端上下文；
- 对于“建联成功、入队成功”等业务结果，由后端在事务成功后写入分析事件；
- 对于“页面已展示、卡片已曝光”等只能由客户端判断的行为，由前端上报；
- 分析报表可以关联两类数据，但不得改变业务审计记录。

赛后只有在同时出现以下需求时，才重新评估第三方或自托管分析平台：需要跨活动留存、复杂用户分群、多人日常查看仪表盘、热图／会话回放，或数据量已不适合 SQLite 查询。接入前必须重新完成隐私、保存期限、数据驻留与删除能力评估。

## 2. 数据模型与公共字段

项目现有 `event_id` 表示活动／展会 ID，容易与“单条埋点事件 ID”混淆。因此分析表使用明确命名：

| Field | Type | Required | Description | Example |
|---|---|---:|---|---|
| `analytics_event_id` | string(UUID) | Yes | 单条埋点唯一 ID，用于去重 | `53b4...` |
| `event_name` | string(enum) | Yes | 本文允许的事件名 | `connection_requested` |
| `anonymous_id` | string(UUID) | Conditional | 登录前的随机设备标识；不得由手机号推导 | `58ca...` |
| `user_id` | string | Conditional | 登录后的内部用户 ID；不得填手机号 | `user-7f1...` |
| `exhibition_id` | string | Yes | 活动 ID | `hackathon-2026` |
| `session_id` | string(UUID) | Yes | 一次前台使用会话 | `8a21...` |
| `source` | string(enum) | Yes | 入口或动作来源 | `online_recommendation` |
| `client_type` | string(enum) | Yes | `android_webview`／`mobile_web`／`backend` | `android_webview` |
| `app_version` | string | Yes | APK/H5/后端发布版本或提交号 | `78b3412` |
| `object_type` | string | No | 被操作对象类型 | `connection_request` |
| `object_id` | string | No | 内部对象 ID | `request-42` |
| `properties` | JSON object | Yes | 事件白名单属性；无属性时为 `{}` | `{"rank":2}` |
| `occurred_at` | ISO-8601 UTC | Yes | 客户端发生时间；后端事件使用服务端时间 | `2026-08-29T13:00:00Z` |
| `received_at` | ISO-8601 UTC | Yes | 服务端接收时间 | `2026-08-29T13:00:01Z` |

约束：登录前必须有 `anonymous_id`，登录后必须有 `user_id`；验证成功后将同一会话中的 `anonymous_id` 与 `user_id` 仅在服务端关联，客户端不得回传手机号用于关联。

### 2.1 Source 枚举

`sms_login`、`online_recommendation`、`nearby`、`nfc`、`qr`、`physical_mutual`、`connections_list`、`project_room`、`direct_link`、`system`。

不能识别来源时使用 `direct_link`，不得使用任意自由文本。NFC 与 QR 必须生成不同的入口参数，并在服务端校验后写入。

## 3. Event Inventory

### 3.1 P0 演示漏斗事件

| Event Name | Producer | Exact Trigger | Event-specific properties |
|---|---|---|---|
| `login_otp_requested` | Backend | 腾讯云短信发送请求被服务端接受，且 challenge 已成功创建后写入；发送失败不写成功事件 | `challenge_id`、`provider=tencent_cloud` |
| `login_otp_request_failed` | Backend | 短信请求在服务端终止为失败时写入一次 | `failure_code`（白名单粗分类）、`retryable`；不得包含供应商原始报文 |
| `login_otp_verified` | Backend | 验证码校验成功、OTP 已一次性消费并签发登录 session 后写入 | `challenge_id`、`new_user` |
| `login_otp_verification_failed` | Backend | 验证失败或锁定后写入一次 | `failure_code=invalid_code/expired/locked/rate_limited`、`attempt_bucket` |
| `event_joined` | Backend | 用户首次成功加入指定活动，membership 已提交后写入；幂等重放不重复写 | `membership_id`、`new_user` |
| `profile_completed` | Backend | 资料从“不满足最小要求”首次变为“满足最小要求”时写入 | `field_count`、`evidence_count`、`completion_version` |
| `visibility_enabled` | Backend | 用户成功公开至少一个允许字段后写入；界面可称“资料发布”，不得另记 `profile_published` | `scope`、`public_field_count`、`expiry_bucket` |
| `discovery_viewed` | Client | 发现页真实数据首屏成功渲染后写入；loading、失败页不写 | `result_count_bucket`、`filter_count` |
| `match_impression` | Client | 某候选卡片至少 50% 可见并持续 1 秒；同一 session、候选人、列表请求只记一次 | `candidate_id`、`rank`、`rule_score_bucket`、`list_request_id` |
| `match_detail_opened` | Client | 用户主动打开真实候选人的详情页且内容渲染成功后写入 | `candidate_id`、`rank`、`reason_count`、`list_request_id` |
| `card_landing_opened` | Backend | 有效卡 token 的公开落地页成功返回后写入；无效／停用 token 不写成功事件 | `card_id`、`owner_id`、`source=nfc/qr` |
| `connection_requested` | Backend | 请求创建事务成功后写入；接口幂等重放不重复写 | `request_id`、`recipient_id`、`source` |
| `connection_accepted` | Backend | 接受动作成功并首次生成 connection 后写入；界面可称“确认建联”，不得另记 `connection_confirmed` | `request_id`、`connection_id`、`latency_seconds_bucket` |
| `touch_handshake_completed` | Backend | 双卡可信握手首次生成唯一 connection 后写入 | `handshake_id`、`connection_id`、`source=physical_mutual` |
| `touch_handshake_failed` | Backend | 握手超时、无效、重复或权限拒绝后写入一次 | `handshake_id`、`failure_code` |
| `project_created` | Backend | 项目事务成功提交后写入 | `project_id`、`origin_connection_id`、`role_need_count` |
| `team_invited` | Backend | 项目邀请首次创建成功后写入 | `project_id`、`invitation_id`、`role_need_id`、`connection_id` |
| `team_joined` | Backend | 受邀者本人接受邀请且 membership 已创建后写入 | `project_id`、`invitation_id`、`role_need_id`、`connection_id` |
| `room_viewed` | Client | 项目启动舱真实数据成功渲染后，同一 session/project 首次写入 | `project_id`、`member_count`、`pack_status` |
| `collaboration_pack_generated` | Backend | 启动包成功持久化后写入，包括模板降级 | `project_id`、`member_count`、`fallback_used`、`generation_source` |
| `task_accepted` | Backend | 用户成功接受／认领任务并完成状态迁移后写入 | `task_id`、`project_id`、`assignee_id` |

说明：按钮点击、请求发出不等于业务成功。凡是有后端状态迁移的事件，一律以后端成功提交为准，前端不得重复上报同名成功事件。

### 3.2 隐私与可靠性事件

| Event Name | Producer | Exact Trigger | Event-specific properties |
|---|---|---|---|
| `guardrail_blocked` | Backend | 服务端成功拦截一次越权公开、过期资料继续曝光、拉黑后请求或未确认入队 | `guardrail_code`、`object_type`、`source` |
| `analytics_batch_rejected` | Backend | 整批埋点因格式、大小或鉴权问题被拒绝 | `failure_code`、`event_count_bucket`；只进服务日志，不再递归写埋点 |

`guardrail_blocked` 表示护栏成功工作，不等于隐私事故。真实事故必须走独立安全事件流程，不能只依赖行为埋点。

### 3.3 暂不纳入 P0

PRD 中的 SOS、支援响应、援助会话、卡片停用、拉黑、实时协作状态等事件保留原定义，但只有对应功能进入真实主演示后才实现。不得为了“事件齐全”给未接入真实后端的静态页面制造假数据。

## 4. 漏斗与指标定义

### 4.1 登录漏斗

`login_otp_requested → login_otp_verified → event_joined`

- 分母：去重后的 `anonymous_id`；
- 短信验证转化：验证成功用户数 ÷ 成功请求短信用户数；
- 同一 challenge 的重复验证码尝试只影响失败诊断，不扩大成功漏斗分母；
- 新用户自动入展与验证若在同一事务完成，允许两个事件时间相同，但顺序由服务端写入顺序保证。

### 4.2 资料公开漏斗

`event_joined → profile_completed → visibility_enabled`

- 按 `user_id + exhibition_id` 去重；
- 只保存完成字段数量，不保存字段正文；
- 暂停后再次公开可以重新写 `visibility_enabled`，但“首次公开率”只取用户第一次事件。

### 4.3 发现与建联漏斗

`discovery_viewed → match_impression → match_detail_opened → connection_requested → connection_accepted`

- 使用 `session_id`、`list_request_id`、`candidate_id` 做一次会话内归因；
- 请求和接受按后端对象 ID 去重；
- NFC／QR 路径使用 `card_landing_opened → connection_requested → connection_accepted`；
- 线上推荐、附近、NFC、QR 分开统计，不混合 source。

### 4.4 协作启动漏斗

`connection_accepted → project_created → team_invited → team_joined → room_viewed → collaboration_pack_generated → task_accepted`

- 归因窗口：建联成功后 72 小时；
- “有效协作结果”至少满足 `team_joined`，或同一项目下出现 `task_accepted`；
- 同一用户加入同一项目、同一任务的幂等重放不重复计数；
- `fallback_used=true` 的启动包仍算可用，但需单独统计降级率。

## 5. User Properties

演示阶段不把姓名、手机号或自由文本复制为分析用户属性。可用于分群的持久属性仅限：

| Property | Type | Description | Set When | Example |
|---|---|---|---|---|
| `user_id` | string | 后端内部随机用户 ID | 验证登录成功 | `user-7f1...` |
| `account_created_at` | ISO-8601 UTC | 账号创建时间 | 首次建号 | `2026-08-29T13:00:00Z` |
| `participant_state` | enum | 当前活动参与状态 | 加入／离开活动 | `active` |
| `profile_visibility_state` | enum | `hidden`／`visible`／`paused` | 可见性变更 | `visible` |

动态的项目数、连接数、技能、兴趣和身份称呼不作为全局用户属性，按业务表在受控查询中计算。

## 6. PII & Privacy Considerations

### 6.1 禁止进入埋点的数据

| Data | PII Type | Handling |
|---|---|---|
| 手机号 | 直接身份信息 | 不发送、不哈希后发送；仅保留在认证业务数据中 |
| 短信验证码、challenge secret | 认证秘密 | 绝不记录 |
| access token、refresh token、Cookie | 认证秘密 | 绝不记录 |
| 姓名／称呼 | 直接或可识别信息 | 不进入埋点；只使用内部 `user_id` |
| 资料正文、项目描述、消息内容 | 自由文本，可能含个人信息 | 不进入埋点；只记录数量、枚举和内部对象 ID |
| 精确经纬度、完整 IP | 位置／网络标识 | 不进入事件属性；位置仅记录粗距离桶，IP 仅按安全限频策略处理 |
| 第三方 OAuth 标识与平台链接 | 外部账号信息 | 不进入埋点 |
| 腾讯云短信原始响应 | 可能包含手机号和追踪标识 | 只映射为白名单 `failure_code` |

内部 `user_id`、`candidate_id` 等仍按可关联的假名化个人信息管理，不得公开导出到无权限环境。

### 6.2 Consent Requirements

- 登录页或首次使用页必须提供可读的隐私说明：收集目的、事件范围、保存期限和删除方式；
- 演示阶段不加载第三方统计 SDK，不向第三方分析域名发送数据；
- 非登录用户只使用随机 `anonymous_id`，不得通过指纹、手机号哈希或广告 ID 追踪；
- 如赛后用于跨活动画像、营销或引入第三方平台，必须重新评估告知、同意和数据处理安排；
- 本规范是工程最小隐私要求，不替代正式法律审查。

### 6.3 Data Retention

- 原始 `analytics_events` 默认保留 30 天；
- 仅保留不含个体标识的聚合漏斗最长 90 天；
- 演示数据重置默认删除演示用户对应的行为埋点，但保留系统配置；
- 支持按 `user_id` 删除分析事件；删除不得破坏业务审计日志的法定或安全保留要求；
- CSV 答辩导出只含聚合值或内部 ID，使用完成后删除临时文件。

## 7. Implementation Notes

### 7.1 SDK / Integration

- **Platform：** Android WebView、移动 H5、Node.js 后端；
- **SDK：** 不引入第三方 SDK；使用同源第一方 HTTP 接口；
- **采集接口建议：** `POST /api/analytics/events`，允许单条或小批量；
- **汇总接口建议：** `GET /api/admin/analytics/summary?exhibition_id=hackathon-2026`；
- **导出接口建议：** `GET /api/admin/analytics/export?exhibition_id=hackathon-2026&format=csv`；
- **管理鉴权：** 使用独立的服务端管理密钥或管理员 session，不把“现场访问码”重新放回普通用户登录流程；
- **域名：** 所有请求继续发往 `https://49.233.197.225`，不新增第三方网络目的地。

### 7.2 Event Timing

- 后端结果事件必须在业务事务成功提交后记录；若分析写入失败，不回滚已成功的核心业务，但必须输出结构化告警；
- 客户端曝光事件可以使用 `navigator.sendBeacon`，不可用时使用 `fetch(..., {keepalive: true})`；
- 弱网允许客户端短暂排队并重试，最多保留 20 条、最长 24 小时；
- 服务端以 `analytics_event_id` 唯一约束去重，重试不得造成重复计数；
- 客户端时间只用于路径排序参考，后端业务结果以 `received_at` 为准；
- 所有属性使用服务端白名单，未知事件名、未知属性、超长值和自由文本直接拒绝或丢弃。

### 7.3 建议表结构

```sql
CREATE TABLE analytics_events (
  analytics_event_id TEXT PRIMARY KEY,
  event_name TEXT NOT NULL,
  anonymous_id TEXT,
  user_id TEXT,
  exhibition_id TEXT NOT NULL,
  session_id TEXT NOT NULL,
  source TEXT NOT NULL,
  client_type TEXT NOT NULL,
  app_version TEXT NOT NULL,
  object_type TEXT,
  object_id TEXT,
  properties_json TEXT NOT NULL DEFAULT '{}',
  occurred_at TEXT NOT NULL,
  received_at TEXT NOT NULL
);

CREATE INDEX idx_analytics_funnel
  ON analytics_events (exhibition_id, event_name, received_at);
CREATE INDEX idx_analytics_user
  ON analytics_events (user_id, exhibition_id, received_at);
```

写库前还需增加应用层事件／属性白名单、单批大小限制、速率限制与 JSON 深度限制，不能仅依靠 SQL 表结构。

## 8. Testing Checklist

### 8.1 Event Validation

- [ ] **login_otp_requested：** 用真实手机号请求短信，确认腾讯云接受且只写一条事件；事件中无手机号、验证码和原始供应商响应；
- [ ] **login_otp_verified：** 输入正确验证码，确认 session 签发后写入，并能将登录前匿名会话关联到内部用户；
- [ ] **登录失败：** 错码、过期、锁定和限频只记录粗粒度失败码，不记录验证码；
- [ ] **profile_completed / visibility_enabled：** 完成最小资料并授权公开，各写一次；接口失败时不写成功事件；
- [ ] **discovery_viewed：** 真实数据成功渲染后写入，loading／错误页不写；
- [ ] **match_impression：** 同一卡片 50% 可见 1 秒后写入，同一列表重复滚动不重复写；
- [ ] **connection_requested / accepted：** 两台手机真实操作，后端状态成功后写入；重复提交不重复计数；
- [ ] **NFC / QR：** 各跑至少 3 次，确认 `source` 不混淆；
- [ ] **team_joined：** 只有受邀者本人确认并生成 membership 后写入；
- [ ] **collaboration_pack_generated：** 正常生成与模板降级均写入，后者必须有 `fallback_used=true`；
- [ ] **task_accepted：** 任务真实状态迁移后写入，刷新或幂等重试不重复计数。

### 8.2 Property Validation

- [ ] 每条事件都有 `analytics_event_id`、`event_name`、`exhibition_id`、`session_id`、`source`、`client_type`、`app_version`、两个时间字段；
- [ ] 登录前事件有 `anonymous_id`，登录后结果事件有 `user_id`；
- [ ] `source`、`failure_code`、`guardrail_code` 只能取白名单枚举；
- [ ] `properties` 中不存在手机号、验证码、Token、姓名、自由文本和精确位置；
- [ ] 客户端伪造 `user_id`、`app_version` 或服务端结果事件时被忽略或覆盖。

### 8.3 Edge Cases

- [ ] 弱网重试不会重复计数，离线超过 24 小时的事件不再发送；
- [ ] session 超时后生成新的 `session_id`，但 `anonymous_id` 保持随机且不含设备指纹；
- [ ] 登出后不继续把新行为绑定到旧 `user_id`；
- [ ] Demo Reset 后旧演示用户埋点按策略清除，卡片配置不受影响；
- [ ] 分析接口故障不阻断登录、建联、入队和 Room 主流程；
- [ ] 未知事件、超大批次、超长属性和高频滥用被拒绝；
- [ ] Android WebView 与手机浏览器生成的事件可通过 `client_type` 区分。

### 8.4 Funnel Verification

- [ ] 完成一次真实主演示后，登录、资料、建联和协作四段漏斗顺序完整；
- [ ] 演示结束后能按 source 查看 NFC、QR、在线推荐的数量和转化；
- [ ] 同一 Connection、Membership、Task 不会因重试重复计数；
- [ ] 导出内容可作为答辩证据，且不包含禁止字段；
- [ ] 连续 10 次主演示的事件完整率为 100%，零容忍护栏事故为 0。

### 8.5 Debug Tools

- 开发环境提供受保护的最近 100 条事件查看或 JSON 导出；
- 生产演示环境只开放受保护的汇总与 CSV 导出；
- 不在普通用户界面显示管理入口、管理密钥或“现场访问码”；
- 每次发布记录 `app_version`，出现漏报时能定位 APK/H5/后端版本。

## 9. 实施顺序与 Definition of Done

文档确认后按以下顺序实现：

1. `analytics_events` 表、白名单、去重、限频和保留策略；
2. 登录、建联、入队、启动包、任务等后端结果事件；
3. 发现页、曝光、详情和 Room 的客户端事件；
4. 受保护的漏斗汇总／CSV 导出；

完成标准：本文 P0 事件全部能按 `exhibition_id`、`source`、`app_version` 查询；连续 10 次主演示无漏报和重复计数；导出无敏感字段；核心业务不依赖第三方分析服务也能正常运行。
